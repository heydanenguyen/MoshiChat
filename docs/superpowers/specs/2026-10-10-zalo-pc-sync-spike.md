# Spike: Zalo PC 26.10.10 "Đồng bộ tin nhắn từ điện thoại" (sync v2) — can a web (zca-js) session use it?

Read-only static analysis of `app.asar`. Nothing executed, nothing sent to Zalo. Extracted to `<scratchpad>\zalo-pc-asar\`; prettified copies in `<scratchpad>\pretty\`.
Offsets are byte offsets (`rg -b`). CA = `pc-dist\compact-app-pc.*.js`, MS = `pc-dist\lazy\main-startup.*.js`, SW = `pc-dist\shared-worker.*.js`, MN = `main-dist\main.js`. zca-js = 2.2.0.

## 0. Headline
- The PC renderer is the **same code base as chat.zalo.me** (`apiType: embed?31:30`, domains `chat-wpa/files-wpa/group-cm.api.zalo.me`, `isWeb()` branches; CA@7765382). Sync v2 rides the **same websocket and cmd-601 control channel zca-js already speaks**.
- Sync v2 is a **phone to client encrypted pull** (server relays; phone must be online and tap "confirm"). v1 (`get_crossdb`/`pull_mobile_msg`, CA@14406858..14408439) is **dead code** in 26.10.10 (defined, zero callers).
- Whether the server accepts a **web-type (30)** session is NOT provable statically. Evidence leans "designed to allow Web" (sec 2) but it is remote-config/server gated. A 1-day, no-crypto probe decides it (sec 4).

## 1. Sync flow
UI strings (`lazy/lang-vi.*.js`): `STR_SETTING_MSG_SYNC`="Đồng bộ tin nhắn từ điện thoại", `STR_CONFIRM_SYNC_DB_COUNTDOWN_TITLE`="Xác nhận trên điện thoại để bắt đầu", `..._COUNTNUMBER_TITLE`="Yêu cầu sẽ hết hiệu lực sau", `STR_MOBILE_SYNC_DB_NOT_RECEIVED_REQUEST_TITLE`="Chưa nhận được yêu cầu đồng bộ?" (resend = wake-up), `STR_SYNC_BANNER_SUGGEST_NEW_SYNC_DESC`="Zalo Web của bạn hiện chưa có đầy đủ tin nhắn gần đây" (shared lang pack, unused in PC bundle).
Entry: Settings > "Sync & backup" (CA@7994034) or banner/auto-sync -> `SyncMessageController.sync()` -> state machine `AS+M` (CA@3705582, pretty `syncmachine.pretty.js`): `init` (generate IK) -> parallel `timeout-handler` + `sync_full` (sync_conversations -> prepare/sync_preview(+recent) -> sync_other_messages).
Steps (pretty `shared.pretty.js` 11330-11700 = class `Go` "sync-session"; MS pretty 92900-93200 = handlers):
1. **Keys**: fresh in-memory Ed25519/X25519 identity key (IK) every run (CA@170844 `IdentityKeyManager.loadNewIdentityKeyPair`, always `isNewKeyGenerated=true` => always needs phone confirm) + ephemeral `ek` per session. Crypto is a **Rust->WASM blob** `libs/libzproto_wasm_bg.*.wasm` (291 KB; curve25519-dalek, exports `zprotoSync2{GetSessionId,CreateMetadataCipher,DecryptMetadata,EncryptMessage,DecryptMessage}`, `zprotoEd25519*`). SW@246241.
2. **Request** = websocket `cmd 590 subCmd 0` (CA@8545622 table `SYNC_MESSAGE:{REQUEST:590,ACK_DELETE_SYNC_SESSION:591,REQUEST_MOBILE_WAKE_UP:592}`; CA@16802093). Frame = 1B ver(1) + uint16 cmd + 1B subCmd + UTF-8 JSON (CA `_send`, same as zca-js `sendWs`). JSON `{reqId, data:{syncId:rand32, syncType:0(SyncFull)|1(OnDemand), ek:b64pub, ik:b64pub, toDevice:0(Mobile), tempKey:"" or one-time, deviceName:os.hostname(), req:{type:"conversation"|"message", priority, queries:[{partition,from,to,limit}], batchSize}, ver:1, ussidx:n}}` (SW@282503). Error `211` => ClientNotSupport (MS@2194711 whitelist). HTTP twin `GET <files-wpa>/api/transfer-sync-v2/request-sync?zpw_ver&zpw_type&params=AES({reqId,data:JSON}) ` cmd 12888 (CA@14408063) exists but is **never called** (ws path only).
3. **Phone confirm**: PC waits for cmd-601 controls `{act_type:"transfer_msg"|"transfer_sync2", act:"transfer_status", data:{status,fromDevice:0}}`, status 1 Active,2 Idle,3 WaitingConfirm,4 Confirmed,5 BypassConfirmed,6 UserReject,7 UserCancel,8 Busy,9 LowStorage,10 Logout (MS pretty 94735-94800; enum CA `SCpg`). No answer => `USER_DONT_CONFIRM` (1107) after `awaiting_mobile_timeout_ms`=600 000; `cmd 592 {syncId,toDevice}` = "resend/wake the phone" (wakeup_timeout 180 000). Auto-sync after QR login: server sends control `transfer_after_login {temp_key, imei==ours}` (valid 10 min, MS@2237727) and phone answers BypassConfirmed (no tap). Dev menu offers server/"arbitrary_temp_key_12345"/empty tempKey (CA@7267378) => tempKey is not strictly validated; manual path = empty key + tap.
4. **Data arrival**: per batch a control `act:"upload_batch" data:{syncId,idx,isLast,err,batchType(MetadataEmbedded|Message),scopes:[{partition,from,to}],msgUrl}` (`msgUrl` = URL on Zalo CDN). PC does a **plain `fetch(msgUrl)` with no cookies/headers** (SW@370145; concurrency 2, 60 s, 3 retries) => binary of repeated `[uint32 LE len][chunk]` (SW pretty 15016 class `Pl`). Pipeline per chunk (SW pretty 12290): **decrypt (WASM; metadata chunk needs ek.priv+ik, yields sessionRecord; message chunks decrypt with that record) -> Zstd decompress -> protobuf** `Sync2.Message.SyncChunk{platform(1:UNSPEC,MOBILE,WEB=2,PC,SYSTEM), partitions[{id, messages[{senderId(1),clientId(2),msgStatus(3),msgType(4),timestamp(5),globalId(6),content(7),meta(8){attachs,mentions,reference,quote,property,ttl}}]}]}` and `Sync2.Conversation.SyncChunk{conversations[{convId,convType,respondedByMe,lastTs,lastGlobalId,lastClientId}]}` (SW pretty 330-560, 15233-15330). Conversation/sender ids are "PC-noised": converted via `GET <profile>/api/znoise?params=AES({fids,gids})` cmd 12390 (CA@2883445).
5. **Dispose**: `cmd 591 ACK_DELETE_SYNC_SESSION {syncId,toDevice,reason}`.
Limits (defaults, MS pretty 94480-94680; overridable by server remote config `sync_2_pc`, whose `enable` default is **false**): conv list unlimited (-1 days/-1 count); preview 10 convs x 1 msg; recent 10 convs x 100 msg; "all remaining" unlimited (days -1, count -1); `transfer_batch_size` 2000 (50..10000), `batch_size` 2000, `conversations_batch_size` 1000, concurrency 4, batch timeout 10 s, phone-idle pause 600 s, fail threshold 50 % / 10 batches. Phone app must stay open (MOBILE_IDLE pauses). Size in bytes: not determinable.

## 2. PC session vs web session
| | PC (26.10.10, win) | zca-js 2.2.0 web |
|---|---|---|
| `zpw_type` / `type` | **24** (mac 23, linux 25), MN@2745716 `getClientType` | 30 (context.js; "embed" build = 31) |
| `zpw_ver` / `client_version` | **692** (ia32 +2000) | 685 |
| `computer_name` | `os.hostname()` (CA@14301033, 14312237) | "Web" |
| imei | `uuid-md5(UA)` stored `z_uuid` (same recipe as web) | `generateZaloUUID(UA)` |
| UA | `ZaloPC-win32-24v692` (MN@2779832) | Chrome UA |
| QR login | `wpa.chat.zalo.me/api/login/reqqr` {language,client_time,imei,computer_name,logged_uids,self_g,qr_form} (CA@554097) | `id.zalo.me/account?continue=zalo.me/pc` |
| ws / REST | identical wire format (ver1+uint16 cmd+subCmd+JSON, AES-GCM cipher key from cmd 1/1, `zpw_enk` secretKey) | same |
The **sync endpoints do not carry a session-type field**; the only client identity is deviceName + the session (type/imei/cookies) the server already knows. Whether the server rejects type 30 is unknown. Indicators it was designed to allow Web: device enum `{Mobile:0, Web:1, PC:2}` (CA@8905875), event `transfer_after_login_web_received` (MS@2243007), config key `enable_success_noti_pcweb`, protobuf `PLATFORM_TYPE_WEB`, the "Zalo Web" lang string. Indicators against: remote config is named `sync_2_pc`, default `enable:false`; phone may require min app version (error 211/1000 `ClientNotSupport`).
The ws control channel already reaches zca-js: `listen.js` decodes cmd 601 `controls[].content.{act_type,act,data}` and ignores unknown types, so `transfer_*` events would arrive (if sent to a web session) without a second connection.

## 3. Other history endpoints in PC but not in zca-js
- **Cloud message store** `https://group-cm.api.zalo.me`: `GET /api/cm/getrecentv2` (12506), `/getoldv2` (12507), `/rgetv2` (12508, jump), `/getpath` (12504); params AES `{groupId (strip leading "g"), globalMsgId, count (PC default cfg), msgIds[], imei, src, isOA}` (CA@2889475, pretty 556985-557025). **Enabled only for groups + "Send-to-me"** (`apiEnable`, CA pretty 62233) => no 1:1 server history; that gap is exactly why phone sync exists. zca-js only has `group/history {grid,count}`.
- `GET <convers>/api/preloadconvers/get-last-msgs` (10053) params `{threadIdLocalMsgId:JSON, imei}` = last message per conv for list previews; `/api/preloadconvers/get-last-seen`, `/api/react/gLastSn` (CA@2868880).
- ws queue pull: `532 VERIFY_MSG`, `533 HAS_MSG`, `534 PUSH_MISS_MSG`, `570 GET_MSG {queueId,ids,lastId,reqId}`, `571 PRELOAD`, `610/611 CTRL_PULL_REACT` (offline-queue gap fill only; zca-js has 510/511 old-message request for the same purpose).
- Backup direction PC->phone: `630..634 BACKUP_MSG.*`, `POST /api/backuppc2mb/upload`, `/api/message/get_backupmsginfo` (not useful).
- No generic "getmsgs for a 1:1 thread" endpoint exists. 1:1 history older than the offline queue lives only on the phone.

## 4. Verdict for Moshi
**(a) Call from the existing web session: POSSIBLE-BUT-UNPROVEN.** Same ws connection (no new session, no kick), same cmd-601 control events, the msgUrl download is cookie-less. Unknown: server accepts type 30; phone-side support for a Web requester; account's remote config. Go/no-go probe (~1 day, no crypto): over the live zca-js ws send `{ver1,cmd590,sub0,{reqId,data:{syncId,syncType:0,ek:rand32b64,ik:rand32b64,toDevice:0,tempKey:"",deviceName:"Moshi",req:{type:"conversation",priority:..,queries:[{partition:"-1",from:0,to:MAX,limit:10}],batchSize:2000},ver:1,ussidx:0}}}` and log (i) the cmd-590 response `error_code`, (ii) whether `transfer_status 3 WaitingConfirm` arrives and the phone shows the prompt. If it prompts, type 30 is accepted and only crypto remains. **Needs user OK: it pops a prompt on the owner's phone (live-system test).**
**(b) Emulate a PC login just for sync: NOT recommended.** Needs a full PC-type login (reqqr QR with type 24/ver 692, computer_name, own imei, own ws). That is a second PC-slot session: per MEMORY a stray Zalo PC run already kicked the real Zalo PC, so it would log out the user's installed Zalo PC (and the trusted-device banner says sessions expire unless the phone is opened). It would not kick the web session (different type) but only if PC and Web slots coexist, which the code does not prove.
**(c) Effort/fragility (assuming (a) passes):** ws send/recv of 590/591/592 + control hooks 1 d; protobuf from generated code 0.5-1 d; zstd + frame parse 0.5 d; `znoise` id mapping 0.5 d; confirm/progress/import UX + retries 1-2 d; **crypto is the cliff**: either drive Zalo's own `libzproto_wasm_bg.*.wasm` as a black box (thin wasm-bindgen glue, 1-2 d; but redistributing/pinning a proprietary blob that is renamed per release) or reverse the Signal-like session in the wasm (>= 1-2 weeks, high risk). Total ~1-2 weeks to a working prototype; **fragility high**: undocumented protocol `ver:1`, server remote-config gated, wasm/hash changes per release, phone-version dependent, plus unofficial-API/ToS account risk.
**Not determined:** server gating on `zpw_type`; the actual cmd-590 response shape/ids; real remote-config values for this account; AES/KDF inside the wasm; payload byte sizes; PC+Web coexistence; whether QR-login via `id.zalo.me` makes the phone offer `needSyncMsg`/`transfer_after_login` for a web login.
**Cheaper alternative worth a look (not analysed):** the installed Zalo PC already holds the synced history in a local encrypted SQLite (`native/nativelibs/db-cross-v4`, `utility-process-sqlite`); key derivation unverified.
